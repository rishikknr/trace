# Future NovaMart multi-source test blueprint

**Blueprint only. No real NovaMart datasets, provider resources, external accounts or fixture deployment were created in this pass.** Obtain explicit authorization and low-privilege test credentials for each external account before running this future scenario.

## Baseline and evidence ledger

Create a dedicated NovaMart test organization and a separate negative-test organization. Record organization/user/team UUIDs and effective roles. Use provider-scoped test identities, a unique S3 bucket/prefix, a Snowflake database/schema allowlist, a dedicated GitHub repository/branch/directory and Power BI workspace IDs. Keep provider credentials in secret storage, never the scenario ledger. Record each connection ID and the raw provider identifiers, configured scope hash, acquisition run/attempt/batch IDs, expected external keys and resulting stable TRACE UUIDs.

The intended chain is a hypothesis until each edge has evidence:

| Segment | Legitimate evidence and TRACE operation | Boundary |
|---|---|---|
| S3 object → Snowflake RAW | Controlled ingestion manifest/job specification or explicit owner declaration; manual DATA_FLOW mapping with evidence reference | S3 inventory alone does not prove ingestion or execution |
| RAW → GitHub SQL → CURATED | Actual file commit/blob and parsed candidates; register immutable formula, then explicitly confirm existing asset/column mappings | GitHub file existence/parsing does not prove the SQL ran |
| CURATED → semantic model | Supported provider/model metadata if actually available, otherwise manual MODEL_SOURCE declaration | Do not invent full model dependencies |
| Semantic model → Power BI report | Accessible report.datasetId from the configured workspace, both objects resolved | Only this supported association may be live-discovered automatically |
| Measure/visual/report usage | Genuine exported mapping or manual declaration; metric version mapped explicitly | Standard REST inventory does not expose all DAX/visual definitions |
| Metric implementation | Registered formula-version reference and explicit version-specific report usage | Registration is not approval or deployment |

Run baseline discovery for each source, review actual preview/completeness/warnings, and commit explicitly. Record counts and UUIDs. Establish manual edges only after reviewing real evidence; label MANUAL_DECLARATION, IMPORTED_MAPPING, PARSED_SQL candidate, LIVE_DISCOVERY observation or UNRESOLVED accurately. TRACE does not currently ingest independently verified EXECUTION_EVIDENCE; do not select that label to imply an execution verifier exists.

## Common case protocol

For every case below, save the initial provider/TRACE state and a read-only fingerprint, perform only the authorized controlled external/manual action, acquire metadata, capture the preview, commit only reviewed changes, and compare UUIDs/counts/history. The acquisition run's completion is not commit. All writes require an active organization plus appropriate OWNER/ADMIN or endpoint team OWNER/EDITOR; viewer writes must fail with a valid CSRF token so the test measures RBAC. Mapping/formula/metric operations name all affected immutable version IDs. Raw evidence and expected/observed states belong in the ledger, not just screenshots.

## Isolation, reconciliation and acceptance ledger

Use fresh scenario organization/team/source identifiers, never another organization's existing fixtures. Export a baseline ledger of provider IDs, external keys, TRACE IDs, source scopes, immutable versions, active mappings and run/batch evidence. Perform one change at a time; after each commit compare the expected and observed ledger, including UUID stability, warnings, omissions, old/new history and potential paths.

Separate provider read-only acquisition permissions from the explicitly authorized actions used to create/change/delete the future test resources. TRACE itself must not perform those external writes. Keep negative organization/viewer tests and byte-preservation checks in every iteration. Renamed external objects/files are new identities unless a separately reviewed reconciliation mechanism exists; do not equate names heuristically.

An unsupported relationship must remain unresolved or manually declared with evidence. Missing provider fields, macro SQL, absent DAX/visual APIs and source disappearance do not justify fabricating execution lineage. Human source-of-truth review remains necessary for semantic impact, complete column expression resolution and manual declaration updates. This blueprint prepares the next assignment; it does not deploy it.
